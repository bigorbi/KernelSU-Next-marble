## FullLTO flag discrepancy: a confirmed experiment error

The saved FullLTO command explicitly supplied:

```text
-ftrap-function=__ubsan_handle_cfi_check_fail_abort
```

The pinned kernel [Makefile](https://github.com/aosp-pablo/android_kernel_xiaomi_sm8450/blob/5c59cd9a314704d30f3f66004183426da23410e1/Makefile#L986) adds that flag only when non-permissive CFI is enabled **and `CONFIG_UBSAN_TRAP` is absent**. The running and rebuilt configurations have `CONFIG_UBSAN_TRAP=y`. Their correct CFI failure mode is a native trap. The control build followed the conditional correctly; the manually assembled FullLTO override did not.

Consequently, this was a two-variable experiment: changing LTO mode also changed trap lowering. It cannot isolate all remaining instruction differences as effects of FullLTO alone.

Confirmed consequences in the actual binary:

- One additional undefined/versioned import: `__ubsan_handle_cfi_check_fail_abort`, CRC `df7a4c69`; 332 imports instead of 331. All 331 original import CRCs are preserved. The added CRC exists in the genuine reconstructed kernel table, but its presence differs from the original module's import surface.
- Exactly **389 additional CALL26 relocations**, all to that handler, across 381 function owners. Separate target analysis confirms all non-handler call-target histograms match, both globally and per function. Histograms do not prove call ordering or path behavior.
- The ROM's `__cfi_check_fail` is 88 bytes and contains six BRK instructions. The FullLTO version is 136 bytes, with six handler calls and no BRK instructions. Its stack/return-address instrumentation also changes because the function now makes calls.
- The extra import adds 64 bytes to `__versions` and causes the additional CFI-symbol-surface mismatch.

These are genuine dependency and failure-path changes. The handler name alone does not make them equivalent to the original native traps. Removing this inappropriate custom handler flag restores the pinned configuration's trapping behavior; it does not disable CFI, enable recovery or remove type checks. The locally corrected probe retains all four CFI flags and now refuses a changed CFI, permissive, LTO or UBSAN trap configuration. A regression test evaluates the actual pinned Makefile conditional with GNU make and checks both its native-trap and handler branches.

## Runtime relocations and CFI fingerprints

FullLTO removes the earlier relocation-count differences in `__jump_table`, `.altinstructions` and `.rodata`. The only remaining runtime histogram mismatch is `.rela.text`: CALL26 increases from **21,293 to 21,682**, exactly the 389 handler calls. Every other runtime relocation-kind count matches, and the independent per-function call-target histogram comparison above isolates the added call target. Equal histograms still do not establish equivalent ordering or behavior.

Independent execution of the FullLTO dispatcher reproduces all **198 original type/target groups and 1,094 accepted jump-table entries**, using 216,612 type/slot probes. It also passes 594 negative type/alignment checks. This validates those accepted target sets, not the handler's failure behavior or every target function's body.

The strict CFI fingerprint failure has three concrete parts:

1. `__cfi_check`: all 9,204 instruction bytes are identical. Its 397 relocations have identical offsets, kinds and target names. Of their addends, 396 shift by exactly +2,208 bytes with the CFI table; the remaining one is unchanged. This particular fingerprint difference is confirmed layout movement.
2. **885** changed `.cfi_jt` fingerprints have identical raw jump-entry bytes. Their independently decoded accepted type/destination sets match. Relocation-sensitive fingerprints still differ as the target bodies move.
3. `__cfi_check_fail`: instruction and failure-path behavior really differ, as described above.

No comparison rule or security gate was relaxed to accommodate these findings. The distinction between proved layout effects and the actual failure-path discrepancy is diagnostic evidence only.

## Source equivalence and unresolved functions

The stricter diagnostic comparison finds **1,422** uniquely paired, resolved exact function matches with FullLTO, versus **1,135** with ThinLTO. There are 722 unproved pairs and 19 ambiguous names; FullLTO has no unmatched normalized function names on either side. Of the 722 unproved pairs, **344 have identical raw instruction bytes**. Their relocated references remain unproved, so they are not promoted to source-equivalence passes.

The other **378** uniquely paired functions have different raw instruction bytes, and **every one contains the additional custom trap-handler calls**. No uniquely paired raw-instruction discrepancy was found outside those callers. This concentrates the next investigation on correcting trap lowering; it does not prove every difference disappears after that correction, or resolve the 19 ambiguous names.

`cam_sensor_i2c_command_parser` and `cam_get_dt_power_setting_data`, previously unexplained, now match under the resolved diagnostic comparison. `cam_ife_hw_mgr_init` reaches the ROM's exact 6,456-byte size and identical raw instructions, but its relocated references still fail the conservative comparison. KMD helper raw instructions also match; the reviewed camera source patch was not applied in this experiment.

Functions with residual size differences beyond the common four-byte growth include the shared-GPIO/resource helpers, `cam_flash_ops`, several hardware initialization helpers and `__cfi_check_fail`. These need comparison after correcting the confounded flag before attributing them to different source or headers. **No enabled camera-source revision change has been proved necessary.** No machine-code splicing or speculative source revision is proposed.
