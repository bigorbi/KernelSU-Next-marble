## Why the five checks failed

### 1. allocatable_sections — real generated-code/data differences, unresolved

Every allocatable section has matching type, flags and alignment. Six sizes differ:

| Section | ROM original | Baseline | Baseline minus original |
| --- | ---: | ---: | ---: |
| .text | 1684720 | 1564368 | -120352 |
| .rodata | 477115 | 478555 | +1440 |
| .data | 930416 | 930456 | +40 |
| .bss | 3461364 | 3461360 | -4 |
| .altinstructions | 27228 | 26376 | -852 |
| __jump_table | 28832 | 19824 | -9008 |

Equal section size is stronger than the kernel loader requires. However, these differences accompany substantially different instructions and static-branch site counts: **1,802 versus 1,239** jump-table entries. They cannot all be dismissed as padding, debug stripping or relocation addresses. The conservative gate stays closed. The unresolved cause is the original module's optimization/LTO/build-header environment, possibly enabled-source differences; no source mismatch has been proved merely from sizes.

### 2. cfi_symbols — linker names/table anchors, resolved as a symbol surface issue

The initial comparison counted 1,102 names in the ROM versus 1,101 in the baseline. It treated internal numeric disambiguators and 32-hex translation-unit suffixes as external ABI. For example, `cam_vfe_camif_lite_resource_start.5613.cfi_jt` versus the unsuffixed spelling, and ROM trace callback names versus baseline names containing `.2d0e731ed6a4c221ec63dcbc3915a68a`.

The extra ROM name is **`$x.cfi_jt`**, a defined, zero-sized, GLOBAL/NOTYPE table anchor at `.text+0x19b2e4`, not a function target. Some baseline group anchors are HIDDEN/NOTYPE rather than ROM LOCAL/FUNC entries; this also explains why v1 did not fingerprint 21 of those aliases. A jump-table alias's symbol size can cover a whole type group and depends on which alias starts that group.

After accounting for these names, the **1,101-name multiset matches**, retaining duplicate counts. Independent ARM64 dispatch execution and decoded branch destinations also match as described below.

The refined symbol-surface rule only normalizes numeric/32-hex suffixes on defined LOCAL or HIDDEN `.cfi_jt` symbols (FUNC or NOTYPE). It preserves public/default-visibility and undefined names exactly. It omits only the explicitly identified, defined, zero-sized NOTYPE `$x.cfi_jt` anchor. Missing duplicates, renamed real targets, nonzero-sized anchors and public/undefined renames still fail. This does not replace the separately required dispatcher/target or compiled-code gates.

### 3. relocation_properties — debug-strip noise plus real runtime differences

The baseline contains five non-allocated DWARF relocation sections absent from the stripped ROM: `.rela.debug_frame`, `.rela.debug_info`, `.rela.debug_line`, `.rela.debug_loc`, `.rela.debug_ranges`. Baseline size is 48,475,912 bytes; an independent `llvm-objcopy --strip-debug` copy is 6,801,256 bytes. Stripping changes **none** of its allocated sections, metadata, CRCs, CFI symbol inventory or v1 function/CFI fingerprints. The ROM is 7,111,784 bytes.

The old rule incorrectly mixed debug relocations with relocations processed when loading a module. The new rule selects relocation sections by their ELF **sh_info target's SHF_ALLOC flag**, never by a `.debug` name exclusion. All relocation counts remain in diagnostics. A missing reference runtime table fails closed.

### 4. cfi_type_dispatch_and_targets — v1 layout fingerprints fail; independent typed destination audit matches

V1 compares entire maps of every CFI-named FUNC fingerprint, including internal names, aggregate alias sizes and raw section-relative relocation addends. The maps have **1,096 versus 1,075** names, only 415 common names and 167 identical records. This is not a semantic CFI dispatch comparison.

Both actual `__cfi_check` functions are 9,204 bytes. Relocation-masked instructions differ in six bytes: the two independent moves at offsets `0x2368`/`0x236c` swap order (`x29 = sp`, `x0 = x2`) in failure setup. Type-table relocation addends move with link layout; the failure helper also moves from `.text+0x2400` to `.text+0xe890`. Internal table spelling and group ordering account for further v1 differences.

`emulate_cfi.py` independently executes the relocated ARM64 dispatcher under Unicorn 2.1.4; it never loads either module into the host kernel. It recovers candidate type IDs from the dispatcher's actual MOV/CMP constants and adjacent optimizer pivots, checks their table bases, then tests every eight-byte slot across the table. It decodes each accepted BTI/B jump destination, including relocation symbol/addend targets.

Result: **198 accepted type IDs and 1,094 entries in both**, with equal type-to-named-destination multisets after documented internal suffix normalization. **433,224 slot/type combinations** were tested across the two binaries, plus **1,188 rejected wrong-type/unaligned-pointer cases**. Redirecting one jump relocation to a different target is detected even though table addresses and type IDs remain unchanged.

This resolves the observed dispatcher/typed-name discrepancy for these binaries. It does not prove the destination bodies equivalent, guarantee every conceivable input for another dispatcher form, or identify historical build inputs. Name suffix normalization remains diagnostic here; the workflow's strict CFI fingerprint gate is retained. No green release result is inferred from emulation.

### 5. compiled_source_equivalence — v1 false mismatches mixed with real code generation changes, unresolved

V1 has 3,997 baseline versus 3,381 original normalized function names; 2,649 are common, with 512 identical fingerprint records. Its raw section-relative addends and internal names are layout-sensitive, so mismatch is not proof of changed C source.

The KMD accessor is **1,116 bytes in both** and packet validator **368 bytes in both**. Their relocation-masked instruction bytes and referenced read-only string hashes match. For example, the same KMD error string moved from `.rodata+96998` to `.rodata+97341`; v1 hashes that changed addend. This is a demonstrated harmless layout mismatch for those selected functions, not a whole-driver source certificate.

Other functions genuinely differ in generated instructions. `__cam_csiphy_get_preamble_status` is **4,124 versus 2,596 bytes**; `cam_a5_deinit_hw` is **852 versus 800**. The ROM has 3,381 FUNC symbols with no 32-hex linkage suffixes; the baseline has 4,045 FUNC symbols and 1,362 symbols carrying such suffixes. Several baseline-only helpers are candidates for different inlining/outlining decisions rather than new source functionality.

The pattern is consistent with a different original module LTO/internalization/optimization pipeline, including a **possible FullLTO module build** versus this ThinLTO baseline. That is an inference, not an established original flag. Clang's [internal naming documentation](https://clang.llvm.org/docs/UsersManual.html#cmdoption-funique-internal-linkage-names) also explains why compiler-generated names alone do not establish source identity. Matching `.comment` identifies the Clang build; it does not identify every original linker option or kernel header tree.

The October 6 Zois reference was an **image-only** boot-kernel job. Its ThinLTO setting and running boot config do not prove the official ROM camera module used that same module configuration. No actual camera compile/link commands are present in that historical job. Changing the boot kernel to FullLTO, altering metadata or changing the camera source pin would be unjustified.

The closest supported camera revision remains `83ff8a6f43d2fd897a6ee262f5965d4a9d75f00a`. Its parent differs only in the two ISPV3 power cases inside disabled `CONFIG_ISPV3` code; selecting the parent cannot resolve these enabled-code differences. Existing packet/source fingerprints support that family, but do not uniquely determine the original enabled-source tree. **The exact original module source revision and code-generation flags remain unresolved.**

## Changes, validation and next required input

Committed refinements:

- Runtime relocation comparison uses actual allocated target sections; the original runtime table is derived read-only from the authenticated ROM module. All previous original fingerprints remain unchanged.
- CFI symbol comparison distinguishes internal linker spelling and the verified zero-sized table anchor from public names/targets, preserving multiplicity. Original binding/visibility/type/size records are non-binary metadata.
- Compatibility JSON now includes section, name, runtime-relocation and function-size deltas. Camera builds use `V=1` to retain actual future compile/link flags.
- Audit regression tests run before cloud compilation. Optional independent ELF/CFI investigation scripts and a checksum-pinned Unicorn wheel requirement are supplied.

Local validation: 15 regression tests pass, YAML/script syntax and all-stage dry runs pass. The full baseline strip-debug test and the independent CFI positive/negative/destination-mutation checks pass. No substantial kernel or camera compilation was performed locally. No original binary or instruction disassembly is committed.

Re-evaluating this same baseline with the refined rules passes **cfi_symbols**, but still fails **allocatable_sections, relocation_properties, cfi_type_dispatch_and_targets and compiled_source_equivalence**. The last CFI failure is still the conservative v1 fingerprint rule, despite the independent typed-destination result. Exploratory mode, historical SUSFS provenance and unresolved request lifetime review independently keep the release gate closed.

The precise remaining build input is the official ROM camera module's actual **compile/link commands and its kernel header/configuration source provenance**: LTO mode, optimization/import/internalization flags and original LLD identity. Those inputs can distinguish a build-pipeline difference from enabled-source differences. The next controlled cloud investigation should test documented module code-generation settings while preserving the pinned boot environment; neither FullLTO nor another source revision is silently substituted in this change.
